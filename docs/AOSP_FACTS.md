-- GOTCHAS --
  * SKEYSEED uses full-length nonces (Ni||Nr as the HMAC key, g^ir as the message); the 8-byte-per-nonce truncation applies ONLY to AES-XCBC/AES-CMAC PRFs. Do not truncate for HMAC-SHA256.
  * The library does NOT normalize the DH shared secret; it passes JCE generateSecret() output straight into HMAC. With the BouncyCastle 'DH' provider that is a fixed 256-byte, left-zero-padded value for group 14. A Rust reimplementation must use fixed 256-byte big-endian g^ir (leading zeros kept), matching RFC 7296 §2.14; if a peer stripped leading zeros keys would diverge ~1/256 of the time.
  * Initial SKEYSEED = prf(Ni|Nr, g^ir) but REKEY SKEYSEED = prf(SK_d_old, g^ir|Ni|Nr) — DH secret first in the rekey case. Child KEYMAT with PFS is also g^ir|Ni|Nr; without PFS it is just Ni|Nr.
  * prf+ counter is a single byte starting at 0x01 and is appended AFTER S (T_n = prf(K, T_{n-1} | S | n)); the previous block is prepended only from T2 onward (T1 has no prefix).
  * IKE SA key slicing order is SK_d, SK_ai, SK_ar, SK_ei, SK_er, SK_pi, SK_pr (all 32 bytes for this suite; 224 bytes total). Child order is SK_ei, SK_ai, SK_er, SK_ar (encryption BEFORE integrity per direction, initiator direction first) — different ordering conventions between IKE and child KEYMAT.
  * HMAC-SHA2-256-128: key length 32 bytes, ICV = first 16 bytes of the MAC. The integrity key length used in the KEYMAT total is the 32-byte key, not the 16-byte truncation.
  * ICV is computed over the entire packet bytes from IKE header offset 0 through the end of the ciphertext (header Length field already containing the final total length including ICV; SK header Next Payload = first inner payload type). For SKF, the 4-byte fragnum/total header is inside the authenticated region.
  * AES-CBC IV is 16 random bytes, per message AND per fragment; padding bytes are random (not zero, not PKCS#7) and only the trailing pad-length byte matters; pad length is 0..15 such that (data+pad+1) % 16 == 0.
  * The receiver requires SK/SKF to be the ONLY top-level payload: the SK payload length must equal (packet length - 28) exactly, otherwise INVALID_SYNTAX.
  * Fragmentation threshold is the total IKE message length > 1280 bytes (not link MTU) and is only enabled when the peer's IKE_SA_INIT response includes notify 16430; the client always sends 16430 in IKE_SA_INIT. Plaintext per fragment is 1196 bytes (1280 - 28 - 4 - 4 - 16 IV - 16 ICV - 16 blocksize), i.e. the encoder reserves a full block for padding so real fragments are ≤ 1280 - (16 - padLen - 1).
  * Only fragment #1 carries the real Next Payload type in its SKF header; other fragments carry 0. On receive, the type is taken only from fragment number 1 regardless of arrival order.
  * Fragments are split at arbitrary byte boundaries of the encoded payload chain (not at payload boundaries); each fragment is independently authenticated and decrypted, and reassembly concatenates plaintexts before parsing.
  * Reassembly has no timeout; a fragment set with a larger Total Fragments count than currently stored resets reassembly, a smaller one is dropped, duplicates are ignored. Reassembly state is per-direction (request vs response) per IKE SA.
  * IKE header version byte is 0x20, flags use only R (0x20) and I (0x08); the Length field for encrypted messages is 28 + SK payload length.

-- GOTCHAS --
  * First IKE_AUTH request contains NO AUTH payload and NO N(INITIAL_CONTACT) with the glue's options; CP comes AFTER SA/TSi/TSr (order: IDi, IDr, N(EAP_ONLY_AUTHENTICATION=16417), N(MOBIKE_SUPPORTED=16396), SA, TSi, TSr, CP). Some peers are order-insensitive but replicate exactly to be safe.
  * CP request always ends with an APPLICATION_VERSION(7) attribute of zero length that the app never asked for; all seven attributes are 4-byte zero-length TLVs (R bit clear). IPv6 address requests are ZERO length (not 17 bytes).
  * Child proposal always includes an ESN transform (type 5, id 0 = no extended sequence numbers) even though the API never exposes it; omit it and the ePDG may answer NO_PROPOSAL_CHOSEN. ENCR carries key-length attribute 0x800E 0x0100. Proposal numbering starts at 1; single proposal so isLast byte = 0 and last transform isLast byte = 0 (non-last transforms use 3, non-last proposals use 2).
  * TSi and TSr are identical: two selectors each (IPv4 any then IPv6 any), ports 0-65535, protocol 0. Both address families are always proposed even if only one internal address is granted.
  * Under IKE_OPTION_EAP_ONLY_AUTH the first response is accepted with NO AUTH and NO IDr; but if the ePDG nonetheless sends AUTH, full digital-signature validation (CERT chain against system trust store when serverCaCert is null, IDr-vs-cert binding, signature) is performed and an AUTH-without-IDr response fails. A CERT-only response is accepted without validation.
  * IKE_OPTION_ACCEPT_ANY_REMOTE_ID only bypasses the string comparison of received IDr vs configured IDr; whatever IDr is received is what gets fed into the post-EAP PSK(MSK) AUTH verification (prf(SK_pr, IDr-body)). If the ePDG omits IDr in EAP-only mode, respIdPayload is null and the post-EAP verification would NPE; the T-Mobile ePDG evidently sends IDr.
  * Post-EAP AUTH uses method 2 (PSK) with key prf(MSK, 'Key Pad for IKEv2'), signed octets = IKE_SA_INIT request bytes || Nr || prf(SK_pi, IDi body without generic header). The IDi body includes the 3 reserved bytes.
  * IDi RFC822 bytes are UTF-8 of the resolved localIdentifier ('$subscriber-id' substituted); IDr FQDN bytes are US-ASCII of the APN string (e.g. 'ims.tmus'), no trailing NUL/dot.
  * Message IDs: IKE_SA_INIT=0, IKE_AUTH#1=1, each EAP round increments by 1, post-EAP AUTH continues the sequence. Increment happens on receipt of the matching response; a response with id == expected-1 is dropped as a retransmit.

-- GOTCHAS --
  * L flag + 4-byte length is sent on EVERY non-empty first/unfragmented client EAP-TLS message (ClientHello, client flight), not just on fragmented ones; continuation fragments never carry L. Do not omit L on unfragmented messages if you want to match the Java client byte-for-byte (EapTlsMethodStateMachine.java:489-502, EapTtlsTypeData.java:103).
  * The client ack / post-handshake empty response is exactly Type=13 + flags 0x00 (EAP Length 6). The same bytes are used for (a) acking a server fragment (M set), and (b) the final empty response after the handshake finishes. Server acks are recognised only when flags have no L/M/S AND zero data; a server 'ack' carrying L with length 0 is NOT treated as an ack and will be fed to TLS as empty data -> unwrap underflow -> close_notify + failure.
  * Inbound reassembly requires L on the server's FIRST fragment (capacity = messageLength); with L absent any data fails as 'more data than declared'. Later fragments may repeat L only with the same total. If the server under-delivers versus the declared total, the TLS engine is fed a zero-padded buffer of the declared length (EapTtlsInboundFragmentationHelper.java:61,108-110).
  * Each server EAP-TLS message must contain whole TLS records for a complete flight: a BUFFER_UNDERFLOW on unwrap (record split across two EAP requests without M) or any non-OK status triggers closeConnection() and a fatal error (TlsSession.java:390-405).
  * Handshake completion is detected only when a WRAP returns HandshakeStatus.FINISHED (Conscrypt TLS1.2 behaviour, TlsSession.java:340-347). If an engine reports FINISHED on the unwrap of the server Finished instead, the code returns TLS_STATUS_SUCCESS with 0 bytes -> buildEapMessageResponse(byte[0]) -> EapTtlsOutboundFragmentationHelper.getNextOutboundFragment throws IllegalStateException (no remaining data) -> EapError -> IKE fails. Likewise any server message that legitimately needs no reply (e.g. a lone NewSessionTicket) crashes the same way. A Rust port must emulate: after unwrapping server CCS+Finished, emit the empty 0x00 response and mark handshake complete.
  * Only one wrap is performed per inbound EAP message; all client records of a flight (Certificate, ClientKeyExchange, CertificateVerify, CCS, Finished) must be produced in that single wrap and are then fragmented at 1024-byte boundaries with an ack round-trip between fragments.
  * TLS 1.2 ONLY (no TLS 1.3), no SNI, no hostname verification, no cipher-suite restriction; with the T-Mobile config validateRemoteCertificate=false the server cert is not validated at all (trust-all). Only the leaf client cert is sent (single-element chain).
  * MSK = first 64 bytes of exporter("client EAP encryption", no context, 128 bytes); EMSK = next 64 and is dropped. Using the TTLS label or adding a context silently yields a wrong MSK and the final IKE_AUTH AUTH verification fails. MSK is used as the IKEv2 PSK: prf(MSK, "Key Pad for IKEv2") then prf over RealMessage1|NonceR|prf(SK_pi,IDi').
  * EAP-Success received before the TLS handshake is complete (i.e. before the client has sent its empty post-handshake response) is a FATAL error, not accepted. EAP-Success/Failure must have Length exactly 4.
  * EAP identity Type-Data is the raw ASCII string with no NUL and no added realm; for the T-Mobile config it is '900999990490257463@prodepdg.t-mobile.com' and is identical to the IKE IDi (ID_RFC822_ADDR). Identifier is always echoed from the request.

-- GOTCHAS --
  * NAT_DETECTION_SOURCE_IP in the request is computed over the FAKE local IP 192.0.2.0 (not your real address) whenever the ePDG address is IPv4 (IkeSessionStateMachine.java:239-244, 6038-6045). If a Rust reimplementation hashes the real address, the ePDG may NOT detect a NAT and may send plain ESP instead of UDP-encapsulated ESP, breaking a userspace data plane. Conversely, the local-NAT check on the response uses the REAL local address (3752-3763) but is then forced true anyway for IPv4 (3782-3785).
  * For IPv4 the library ALWAYS ends up on port 4500 after IKE_SA_INIT provided the server echoed NAT-D payloads; the only way to stay on 500 is if the server omits both NAT-D notifies. The 4500 socket is a NEW socket with a NEW ephemeral local port (IpSecManager UDP-encap socket), not a rebind of the port-500 socket.
  * On port 4500 every IKE datagram is prefixed by a 4-byte zero non-ESP marker in both directions; on port 500 there is none. Inbound 4500 datagrams whose first 4 bytes are non-zero are dropped as ESP.
  * Transform order inside the proposal is ENCR, INTEG, DH, PRF (PRF last, not the RFC's usual ENCR/PRF/INTEG/DH). Key-length attribute is TV format 0x800E 0x0100. Proposal SPI size is 0 in IKE_SA_INIT (no SPI bytes).
  * Payload order is SA, KE, Ni, N(NAT-D src), N(NAT-D dst), N(FRAG_SUPPORTED), N(SIG_HASH 00 01 00 02 00 03 00 04). NAT-D payloads are omitted entirely for an IPv6 remote. When retrying with COOKIE, the COOKIE notify becomes the very first payload and everything else (same nonce/KE/SPI) follows unchanged.
  * The critical bit is never set on any outbound payload, even though the outbound KE payload object is constructed with critical=true.
  * Retransmit schedule is fixed 0.5/1/2/4/8 s (total 6 transmissions, ~15.5 s to failure) and resends the identical bytes; a COOKIE retry resets the schedule.
  * Response acceptance requires: I flag clear (else SPI demux drops it), msgId 0, version major 2, exact length field, exchange 34, exactly one proposal whose number matches a request proposal and whose 4 transforms are each a member of the request lists, KE group == request group, and SA/KE/Ni all present. Any error notify (type<=16383) other than a recoverable INVALID_KE_PAYLOAD is fatal.
  * SIGNATURE_HASH_ALGORITHMS and CERTREQ handling exist even with EAP-only auth; the peer's hash list is parsed and stored but the request still advertises SHA1/256/384/512.
  * A datagram of 4096 bytes or more on the raw socket is silently discarded (RCV_BUFFER_SIZE=4096, IkeSocket.java:70,177-185) -- large IKE_SA_INIT responses (many CERTREQs) would be lost.

-- GOTCHAS --
  * MACedIDForR uses the IDr from the FIRST IKE_AUTH response (the one that started EAP), re-encoded as idType||00 00 00||idData with NO generic header. If the ePDG omits IDr in that first response, IkeAuthData.respIdPayload is null and the library would NPE in the post-EAP verify (the EAP-only shortcut at ISSM:4367 returns OK without checking IDr presence). A Rust port must capture IDr from the first response, not the last.
  * RealMessage1 is the encoded IKE_SA_INIT request INCLUDING the 28-byte IKE header and, if a COOKIE round-trip happened, it is the SECOND (cookie-bearing) request. RealMessage2 is the raw received IKE_SA_INIT response bytes (with header), not a re-encoding — any byte the responder sent (including unknown payloads, vendor IDs, padding) is part of the signed data.
  * The nonces in SignedOctets are the nonce payload DATA only (generic header stripped); the responder nonce is whatever length the ePDG sent (16..256), the initiator nonce is 32 bytes.
  * The key pad is exactly 17 bytes with no NUL terminator; the outer key is prf(MSK, pad) with the full 64-byte MSK as the HMAC key (JCE HMAC pre-hashes keys longer than the block size; a Rust HMAC crate does the same, but do not truncate MSK to 32 bytes).
  * The post-EAP IKE_AUTH request contains ONLY the AUTH payload inside SK (next-payload byte of the SK payload = 39). No IDi repeat, no notifies, no SA/TS/CP.
  * IDi body for the glue is ID_RFC822_ADDR (type 3) with UTF-8 bytes of resolvedInitiatorId; the EAP identity is the same string but US-ASCII bytes — they may differ if non-ASCII characters are present.
  * The responder's final AUTH MUST be method 2 (PSK/MSK-based); a responder that answers the post-EAP request with a certificate-based AUTH (method 1/14) is rejected outright.
  * EAP-TLS MSK must be exported with label "client EAP encryption", null context, 128 bytes; MSK = bytes[0..64]. Using the TTLS label ("ttls keying material") produces a wrong AUTH silently (the code comment at TlsSession.java:100-101 calls this out).
  * N(EAP_ONLY_AUTHENTICATION) is never expected back; absence of AUTH in the first IKE_AUTH response is the only signal that EAP-only was accepted. Conversely, if the ePDG DOES send AUTH+CERT in the first response, the library will try full certificate validation against the system trust store (trustAnchor=null) and fail if it cannot build a chain.
  * Message ID bookkeeping: IKE_SA_INIT=0, first IKE_AUTH=1, then +1 per EAP round; the post-EAP AUTH request ID = 1 + number of EAP IKE_AUTH exchanges.
  * For the first child, the library reuses the IKE_SA_INIT Ni/Nr payloads as the child nonces (added to the req/resp payload lists before validation); the final IKE_AUTH response itself must NOT be expected to carry a Nonce payload.
  * Both the IKE-level CP attributes (P-CSCF 20/21, APP_VERSION 7) and child-level CP attributes (INTERNAL_IP4/6_ADDRESS/DNS) are sent in ONE CFG_REQUEST in the first IKE_AUTH request and read back from ONE CFG_REPLY in the final IKE_AUTH response; a CP with configType != 2 in the reply is silently ignored (no failure, but no addresses).
  * On any failure validating the final IKE_AUTH response the library does NOT send an IKE Delete (isServerExpectingMoreEap=true), except for protected decode errors where it does.
  * MSK is never null and there is no PSK fallback in the EAP path; a non-key-generating EAP method cannot complete because EapSuccess construction requires a >= 64-byte MSK and EMSK.

-- GOTCHAS --
  * The client fakes a local NAT for any IPv4 ePDG (needEnableForceUdpEncap), so T-Mobile will see NAT_DETECTION_SOURCE_IP that does not match and will expect all ESP UDP-encapsulated on 4500 with a 4-byte zero non-ESP marker for IKE; a Rust port that computes the honest NAT hash will end up on port 500 / raw ESP with different keepalive behaviour.
  * Keepalives: 0xFF single byte to remote:4500 from the same UDP socket as IKE, every 10 s (default), starting immediately when the encap socket is adopted after IKE_SA_INIT — not gated on the peer's keepalive support.
  * DPD only fires after 120 s of Idle with NO other exchange (alarm is cancelled on every state change) and is an empty SK INFORMATIONAL; retransmit schedule 0.5/1/2/4/8 s, 5 sends total, then the session is dropped WITHOUT sending DELETE.
  * For the first child SA (IKE_AUTH), nonces for validation and KEYMAT come from IKE_SA_INIT Ni/Nr; there is no Nonce payload in IKE_AUTH. KEYMAT = prf+(SK_d, Ni|Nr) with no g^ir because the first-child proposal strips DH transforms.
  * Child SPI direction: our SAi2 SPI is the INBOUND (decrypt) SPI; the responder's SAr2 SPI is the OUTBOUND (encrypt) SPI. DELETE(ESP) we send carries our inbound SPI; the peer's DELETE carries their inbound SPI (= our outbound). REKEY_SA notify carries our inbound SPI.
  * ESN transform is always sent with ID 0 (no extended SN) and the responder must select it; the library only recognizes ESN IDs 0/1.
  * CFG_REQUEST attribute order matters for byte-exact interop: child attrs (IP4_ADDR, IP6_ADDR, IP4_DNS, IP6_DNS, then auto-added IP4_NETMASK), then IKE attrs (IP4_PCSCF, IP6_PCSCF), then APPLICATION_VERSION — all with length 0. Only one CP payload, placed after the child SA/TSi/TSr in the last IKE_AUTH request.
  * INTERNAL_IP6_ADDRESS reply value is 17 bytes (addr + prefix byte); exactly 16 bytes is rejected as InvalidSyntax. INTERNAL_IP6_DNS and P_CSCF_IP6 are exactly 16. A CP reply with INTERNAL_IP4_NETMASK but no INTERNAL_IP4_ADDRESS, or two netmasks, is a fatal InvalidSyntax on the whole message.
  * TS response acceptance is strict containment per selector, but the responder may drop the IPv6 selector entirely (e.g. reply TSi/TSr with only the v4 range) and that is accepted; the negotiated TS becomes exactly the responder's selectors.
  * IKE delete response must carry zero payloads to validate cleanly; child delete response must include our remote SPI in a DELETE(ESP) or the child treats it as InvalidSyntax (unless a simultaneous delete was seen).
  * Message-ID handling: separate local/remote counters both reset to 0 on a rekeyed IKE SA; a peer request repeated with id==expected-1 gets the cached response re-sent, so cache the last response packets per SA.
  * The soft-lifetime 'retry' path (rescheduleRekey) ignores its 15 s argument and re-arms at the full soft lifetime; do not model a 15 s rekey retry.
  * Remote-initiated rekeys (IKE or child) are considered complete after 180 s without the peer's DELETE; the client does not send DELETE for the old SA in that direction.
  * TEMPORARY_FAILURE is returned (INFORMATIONAL response) for any peer request other than DELETE_IKE/generic-info while the client is busy, and the client itself retries on TEMPORARY_FAILURE for up to 5 minutes before closing.
